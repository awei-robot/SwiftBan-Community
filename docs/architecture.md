# SwiftBan 架构设计

## 一、设计目标

| 目标 | 实现 |
|------|------|
| 无依赖 | 纯 Bash + 标准 GNU 工具，无需 Python/Go 运行时 |
| 低侵入 | 只读日志，通过 iptables 封禁，不改 Nginx 配置 |
| 防误封 | 只封明确攻击特征；双层白名单；观察模式 |
| 高可靠 | 状态持久化，规则丢失自动恢复 |
| 易运维 | CLI 管理，配置分离，定时任务 |

## 二、模块划分

```
bin/swiftban.sh          CLI 入口（命令分发）
lib/
  config (内嵌)          配置加载与默认值
  logger.sh              日志与审计
  firewall.sh            防火墙抽象（iptables/ip6tables）
  whitelist.sh           白名单（IP/CIDR/文件）
  detector.sh            检测引擎（11 维度）+ 状态管理
```

## 三、数据流

```
Nginx/NPM access.log
        │
        ▼
┌──────────────────┐
│ 1. 文件收集      │  最近3分钟修改的活动及未压缩轮转文件，同 inode 只读一次
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 2. 解析/过滤     │  识别 NPM standard/proxy、combined；按日志偏移转 UTC
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 3. 特征统计      │  标准化字段一次 awk 聚合，窗口过滤及轮转重叠去重
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 4. 决策          │  白名单检查 → 阈值比较 → 封禁/观察
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 5. 执行          │  iptables -I DOCKER-USER -s IP -j DROP
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 6. 持久化/恢复   │  banlist.txt / 规则自动恢复 / TTL 解封
└──────────────────┘
```

## 四、关键设计决策

### 4.1 为什么用 DOCKER-USER 链

Docker 端口映射流量路径：`PREROUTING(DNAT) → FORWARD → 容器`，不经过 `INPUT` 链。`DOCKER-USER` 是 Docker 官方预留给用户自定义规则的唯一链，位于 FORWARD 路径。

### 4.2 为什么按条目时间过滤

早期版本只按文件 mtime 过滤，导致统计跨数天的日志（阈值失效）。现在先用 `find -mmin -3` 收集最近3分钟修改的活动日志与未压缩轮转文件，再严格按条目时间及 WINDOW 过滤。文件预筛选固定为3分钟，不随 WINDOW 扩大；超过3分钟未修改的文件不参与本轮统计。相同日志家族跨文件采用完全相同行的最大重数，保留单文件重复请求，保守避免 copytruncate 重叠导致误封。

### 4.3 为什么只封明确特征

生产实测：按请求总数封禁会误伤微信小程序用户（单 IP 2 万+ 正常请求）。因此改为攻击特征驱动，高频 200 请求仅记录观察。

### 4.4 时区处理

日志可以使用 UTC 或其他明确的 `±HHMM` 偏移。解析器在 `TZ=UTC` 下构造墙上时间并减去日志偏移，严格校验日期，保留 `now - WINDOW <= epoch <= now`。未来时间拒绝，分钟分组使用 UTC epoch 分钟，与服务器本地时区无关。

### 4.5 统一解析与安全失败

NPM standard、NPM proxy、combined 统一输出 TSV：`epoch、IP、最终状态码、方法、Host、完整 URI、UA、Referer、来源文件`。仅从结构化客户端位置提取经过校验的 IPv4/IPv6；引号字符串内的 `[Client ...]` 不具有身份意义。proxy 缓存和多值上游状态不影响最终状态码或 URI 位置。默认逐行自动识别，也可显式指定格式。

路径规则只匹配路径，可疑 UA 只匹配 UA，载荷分别匹配 URI、UA、Referer，不跨字段拼接。保留转义文本；空 UA 接受 `-` 和空字符串；尾部扩展字段不会改变已识别字段的位置。

未知或非法记录跳过并按来源计数；文件枚举、读取、解析程序或统计失败时，本轮不新增封禁并返回非零。正常运行的恢复和 TTL 解封在扫描前完成；dry-run 不执行这些写操作。

## 五、检测维度（11 项）

| # | 维度 | 数据特征 | 阈值 |
|---|------|---------|------|
| 1 | 域名扫描 | 状态码 444 | 10/2h |
| 2 | 扫描探测 | 404/400 计数 | 100/2h |
| 3 | 恶意路径 | URI 正则 | 3/2h |
| 4 | 漏洞载荷 | 完整 URI / UA / Referer 分别匹配 | 2/2h |
| 5 | 可疑 UA | UA 正则 | 5/2h |
| 6 | 登录爆破 | 登录路径 401/403 | 20/2h |
| 7 | 单接口高频 | IP + 域名 + 完整 URI | 200/2h |
| 8 | 单接口速率 | 上述分组 + UTC 分钟 | 30/min |
| 9 | 空 UA | UA 字段为 `-` 或空字符串 | 20/2h |
| 10 | 高频观察 | IP 总请求 | 500/2h（仅记录）|
| 11 | 双栈 | iptables + ip6tables | - |

## 六、状态与持久化

```
/etc/swiftban/state/
├── banlist.txt     封禁记录: IP|时间戳|TTL|原因
├── ban.log         操作审计日志
├── whitelist.txt   动态白名单（IP/CIDR）
└── cron.log        cron 执行日志
```

**恢复机制**：cron 每次运行先 `restore`（规则丢失自动重建），再 `unban_expired`（TTL 到期自动解封）。

## 七、安全边界

- 白名单 IP 静默跳过，不产生日志噪音
- 内网网关默认白名单（192.168.224.1、172.17.0.1 等）
- 单实例锁（flock）防止并发
- 观察模式（WATCH）避免误伤未知业务

单接口分组保留查询参数；NPM 使用小写 Host，combined 缺少 Host，使用活动日志家族文件标识隔离站点。

## 八、性能

当前实现仅读取符合名称规则、最近3分钟内修改的未压缩日志，再按条目时间过滤，避免扫描长期未修改的历史文件。解析器逐行处理，仅对窗口内记录保留轮转去重数据；统计阶段使用一次 awk 聚合。成本随入选文件总大小及窗口内不同记录数增加，上线前应使用实际日志规模验证耗时、临时磁盘空间和内存；旧实现的性能数值不作为此版本保证。
